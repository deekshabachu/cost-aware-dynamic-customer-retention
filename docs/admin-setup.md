# Local administrator setup

The administrator signs in separately from customers. The administrator credential is configured locally and does not create or promote a database user. Customer tokens cannot access the administrator APIs.

For the complete local faculty-demo setup, run `scripts/setup_local_demo.ps1` from PowerShell at the repository root. It prompts for an administrator password and two separate demo customer passwords, hashes them using the existing salted scrypt implementation, and writes only the administrator email, password hash, and authentication signing key to the Git-ignored `.env.local` file. Customer password hashes are updated only for the seed-verified Customer 01 and Customer 02 rows. It does not change customer IDs, orders, snapshots, predictions, or retention decisions.

Start the API using `scripts/start_local_demo.ps1`. This script explicitly loads `.env.local` into the backend process environment, sets the existing SQLite database URL, and starts Uvicorn with the project `.venv` Python. The app does not automatically load `.env.local`; use this startup script. The saved signing key is reused across restarts so existing signed sessions remain valid until their normal expiry.

For the local-only academic demonstration configuration, administrator and customer passwords must contain 4 to 128 characters. This intentionally weak minimum is for demonstration convenience and is not a production security policy. Passwords are still stored as salted scrypt hashes. Do not place plaintext passwords, password hashes, or the signing key in tracked files. The administrator token is separate from customer tokens and uses reserved subject zero; customer account IDs remain positive and cannot authorize admin routes.

To set or change only Customer 04's local password, run `.\scripts\setup_local_demo.ps1 -Customer04Only` from the project root in PowerShell. The script verifies the existing seeded account and prompts for a matching password twice without echoing it. It updates only Customer 04's salted scrypt password hash; it does not change the admin or other customer passwords, `.env.local`, or any customer activity, orders, predictions, retention decisions, claims, or redemptions. Customer 04's email is `customer04@demo.customer-retention.local`.

Budget changes are saved in the SQLite database. Saving the budget does not change customer decisions. In the admin dashboard, set the business eligibility threshold and select **Evaluate All Customers & Generate Offers** to run one persisted bulk evaluation using the saved budget. The threshold affects eligibility only; the saved model still supplies each churn probability. Customers without a valid feature snapshot are reported as missing. The run summary is saved in the database.

Bulk evaluation preserves redeemed interventions and active, unexpired paid offers, excludes those customers from duplicate assignment, and reserves their existing costs against the budget. New decisions use the existing retention policy and are committed together with predictions and the run summary. For the local demonstration, restart the backend with `scripts/start_local_demo.ps1` after code updates. Do not use the legacy `/admin/retention/allocate` API route for the protected-offer demonstration; it retains its older superseding behavior.
